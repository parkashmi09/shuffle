One database, not one per service

This is the load-bearing decision. A sports bet must debit a wallet in a single transaction; splitting those across databases trades a real ACID guarantee for a distributed-transaction problem. So the split is at the service boundary instead:

Exactly one service writes a given table. Everyone else goes through its API.

Each service loads only the model domains it owns, which is declared per module and collected at boot by collectDomains():

The internal surface

Service-to-service calls go to /internal/<service>/… and are guarded twice. First the gateway refuses to route them at all — the check runs on the raw URL, before the legacy rewriter could synthesize such a path, and matches /internal/ anywhere in the path rather than only at the start. Second, the receiving service requires a real internal key.

The key story is more interesting than "one shared secret", and internalAcl.js explains why it changed:

Shared key

Every service holds the same INTERNAL_API_KEY, so internalAuth could only ask "is this THE key?" — always yes. Any service could call POST /internal/user/wallet/credit, which mints balance. The caller also self-declared its name in a header, and that header was written onto audit rows.

Per-service keys + ACL

Each service gets its own key, so the caller is identified by which key verified, not by what it claims. Audit attribution becomes a fact. Then a table decides what each caller may reach — casino and sports may credit, admin and user may not.

Backwards compatible by design

With per-service keys unconfigured, the platform falls back to the shared key, the caller is not identified, and the ACL is skipped entirely — an unmigrated deployment behaves exactly as before. Enforcement is only possible where identity is real, so the two changes ship in that order.

02

The module system

The central abstraction. A module declares itself and never mounts itself — which is what makes forgetting an auth guard impossible rather than unlikely.

A module is a self-contained feature folder exporting a manifest. Nothing outside it needs to know how it works, and it never requires the database or an upstream client directly.

services/user/src/modules/bonus/index.js
module.exports = {
  name: 'bonus',
  service: 'user',
  basePath: '/bonus',
  models: ['core', 'extended'],
  routers: {
    user:  require('./routes/user.routes'),
    admin: require('./routes/admin.routes'),
  },
};

Each router is a factory (deps) => Router, not a built Router. That is what keeps a module free of singletons: the same module can be mounted twice against two different containers in a test, and the whole platform can run as four microservices or as one modular monolith (npm run dev:mono) without a module knowing which it is in.

Four audiences, four guards

The router keys are audiences, and the loader — not the module — attaches the guard.

AudienceMounts atGuard applied by loader
public/api/v1/<svc><basePath>none
user/api/v1/<svc><basePath>authenticate() → requireActive()
admin/api/v1/admin/<svc><basePath>authenticateStaff() + per-route permission
internal/internal/<svc><basePath>internalAuth(key) + ACL

public and user mount at the same path. Audience is a guard level, not a URL segment.

Three refusals at boot

The loader does not trust the convention — it enforces it, and a violation stops the service from starting rather than producing a hole nobody notices.

How a guard is recognised — and why the obvious version failed

To check "does this route carry authorization?", the loader has to identify authorization middleware inside an Express layer stack. The first implementation matched on function name. Three things break that, and the third bit immediately:

  • a rename is invisible to the check
  • asyncHandler erases the name of anything it wraps
  • a test that stubs auth with anonymous arrows produces guards the checker cannot see — so a correctly-guarded module failed to mount and the suite went red

So a registry symbol is stamped instead, and anything unstamped is treated as not authorization — the safe direction to be wrong in.

moduleLoader.js:139 — a tag is a contract
const IS_AUTHORIZATION = Symbol.for('ibitplay.authorizationMiddleware');

Symbol.for rather than an imported constant, because @ibitplay/common cannot require @ibitplay/auth — auth depends on common, and the cycle would be real. A registry symbol is the same value in both packages without either importing the other.

There is one escape hatch, and it is deliberately a sentence: a router may set router.authorizationReviewed = '<why>'. It appears in the boot log, so an exemption is a claim somebody made and can be read back, not a silent boolean.

Anatomy of a module folder

modules/<module>/
├── index.js                the manifest — name, basePath, routers, models, jobs
├── <module>.service.js     the logic. No Express, no SQL strings.
├── <module>.repository.js  where SQL lives, when the module needs raw statements
├── <module>.validators.js  zod shapes, .strict()
├── <module>.errors.js      defineErrors('NAMESPACE', {...})
├── <module>.constants.js   every literal that appeared twice
├── controllers/            thin — unwrap the request, call the service
├── routes/                 public | user | admin | internal
├── sockets.js              socket events, if any
└── __tests__/              against a real PostgreSQL, never mocked away

The layering rule: routes wire, controllers unwrap, services decide, repositories touch SQL. A .service.js containing an Express reference or a SQL string is a smell — that is why BonusService and WalletService are directly unit-testable and why the same settlement code runs from both an HTTP request and a cron tick.

Life of a request

Tracing POST /api/v1/user/bonus/claim/daily from the socket to the ledger row.

At the gateway

The ordering here is the security boundary. Step 1 stops a client claiming an identity; step 3 stops it reaching the service-to-service surface.

  1. 01stripHeaders()Delete spoofable identity headers before anything downstream can read them.
  2. 02verifyToken()Verify the player JWT once at the edge, not four times in four services.
  3. 03Block /internal/*Tested on the raw URL, before any rewrite could produce such a path.
  4. 04Legacy path rewritePOST /api/gis/games/init → /api/v1/casino/gis/launch. verify:modules fails the build if a rewrite points at a route that is not mounted, so the table cannot drift.
  5. 05Proxy by longest prefixSee the trap below.
The 161-route trap

/api/v1/admin/<service>/… does not belong to admin-service. admin is an audience — the loader mounts every service's admin router under it. With only /api/v1/admin → admin in the routing table, 161 admin routes answered 404 through the gateway (101 user, 33 casino, 27 sports) while working perfectly when called directly. Hence three longer, explicit prefixes sorted ahead of the fallback.

Inside the service

createApp() builds the middleware stack every service shares, in an order where each position is argued for:

  1. 01trust proxyOtherwise every request appears to come from the gateway's IP and per-IP rate limiting collapses into one shared bucket.
  2. 02requestContext()Mint or propagate the request id first, so everything after it — including errors — can be correlated.
  3. 03helmet + CORSThe service refuses to boot if CORS_ORIGIN is * in production while credentials are on — with an origin callback that reflects any Origin, it is CSRF with the response body included.
  4. 04express.json()Keeps req.rawBody. Provider webhooks sign the bytes; re-serialising the parsed object can reorder keys and produce a different digest.
  5. 05pino-httpAfter context, so the request id is on every line. Health checks excluded from logging.
  6. 06Request timeout → 504A stuck upstream must not pin connections open until the process runs out of sockets.
  7. 07Rate limitingAfter logging, so throttled calls are still visible.
  8. 08Mounted module routesGuard → validate → controller → service.
  9. 09notFound() → errorHandler()Always last.

Validation replaces, it does not merely check

validate() swaps the parsed result into req.body / req.query / req.params. Because zod objects drop unknown keys and every schema is .strict(), an unrecognised field is a 400 rather than something silently ignored — "which is how user_id in a request body became an account takeover in the source this replaces."

The controller is deliberately trivial

modules/bonus/controllers/index.js
claim: asyncHandler(async (req, res) =>
  response.ok(res, await service.claim({
    userId: req.user.id,          // ← from the VERIFIED TOKEN
    type: req.params.type,        //   never the body, never the query
  }))
),

That single substitution — req.user.id instead of req.body.userid — is the fix for an entire class of legacy bug. The old platform authenticated with checkRole, which read a static role-key header and looked it up in roles_keys: one key per role, shared by every client. Holding it made you "a user", not "this user", and the player was then named by a query parameter.

One envelope, declared errors

success → { success: true,  data: <payload>, meta?: { pagination: {...} } }
failure → { success: false, error: { code, message, details? } }

Errors are declared per module rather than thrown inline. defineErrors('BONUS', {...}) builds factories with a status and a stable code, registers them in a global map at require-time, and throws at boot if two modules ship the same code with different meanings. The payoff: every failure a module can emit is readable in one file, so the API surface is documentable without grepping for throw.

A bug worth knowing about, because it was silent

response.paginated() originally took findAndCountAll's {rows, count}. Most call sites passed the rows array plus a total instead. Destructuring {rows, count} from an array yields undefined for both, and the defaults turned that into a 200 with data: []. Every list endpoint written that way answered empty — no error, no log line. It now honours both shapes.

04

The money spine

Everything else orbits this. Four rules, all enforced in code rather than by convention.

WalletService is the one place a balance changes on the intended path. Casino and sports never run UPDATE credits — they call the internal API, so row locking, ledger writes and idempotency exist in exactly one implementation to get right and one to audit.

The invariant the whole design serves:

credits.<currency>  ==  SUM(credits_ledger.amount)  for that user + currency

GET /internal/wallet/:userId/reconcile checks it. If it ever fails, money moved outside the primitive.

Rule 1 — a currency code never reaches SQL

credits is column-per-currency: 28 columns, btc, eth, usdt, inr… Turning a code into a column name is an injection sink, and UPDATE credits SET ${coin} = … appeared four times in the legacy source.

wallet.constants.js — the allow-list is the boundary
function resolveColumn(currency) {
  const code = String(currency || '').toUpperCase();
  if (!Object.prototype.hasOwnProperty.call(CURRENCY_COLUMN, code)) {
    throw ... // UNSUPPORTED_CURRENCY
  }
  return CURRENCY_COLUMN[code];
}

The hasOwnProperty guard is load-bearing: without it, resolveColumn('constructor') returns a function off the prototype chain. Callers pass the result into Sequelize, never the input.

Rule 2 — lock before reading a balance

   NO LOCK                          WITH LOCK
   A reads 100                      A locks, reads 100
   B reads 100                      B blocks…
   A writes 40                      A writes 40, commits, releases
   B writes 40   ← wrong            B reads 40, rejects 60  ← correct

Verified by test: ten simultaneous debits of 20 against a balance of 100 produce exactly five successes, five rejections, and a final balance of 0.00000000.

Rule 3 — Postgres decides insufficient funds, not JavaScript

wallet.repository.js:178 — the row count is the answer
UPDATE credits SET "btc" = "btc" - :amount
 WHERE uid = :uid
   AND COALESCE("btc", 0) >= :amount
 RETURNING "btc" AS balance

Zero rows returned is the insufficient-funds signal, and nothing was written. Legacy read the balance, compared it in JavaScript, then wrote — and separately clamped the number written to history at zero while decrementing the column unclamped, so history recorded 0 while the balance said −50.

Rule 4 — every movement is idempotent and ledgered

#move() is the single implementation both directions share — "a credit path that drifts from the debit path is how you end up with idempotency on one and not the other."

  1. 01Replay checkfindByIdempotencyKey → return the original movement, shaped identically, and move nothing.
  2. 02Lock the walletCreates the row if crediting a player who has never held a balance. A debit against a missing wallet is insufficient-funds, not a 404 — that is what it means to the caller.
  3. 03Guarded UPDATERule 3.
  4. 04Write recordscredits_ledger (signed, so summing reconciles) + wallet_history, in the same transaction.

Idempotency is checked twice on purpose: the lookup handles the common case cheaply, and a unique index handles two concurrent retries that both pass the lookup before either inserts. A key reused with different parameters is a 409, not a silent replay — that is a caller bug, and hiding it would be worse. The key is derived from the thing being paid for (bonus:<awardId>, casino:dice:<round>:payout), never from a timestamp — a key that changes on retry is the same as having no key.

Compensating refunds

A stake is debited before a round resolves. If anything after that fails, the stake is refunded and the ledger records why. A rollback is itself a movement: its own ledger row, its own idempotency key, referencing the entry it reverses. The original row is never deleted.

If the refund itself fails there is nothing left to try in-process, so it is logged at fatal with everything needed to reconcile by hand:

STAKE NOT REFUNDED — player was debited for a bet that never completed.

Swallowing that would turn a visible inconsistency into a silent one.

Money is never a float

packages/common/src/money.js works in BigInt minor units at scale 8 and converts to a decimal string only at the edges. The two parse functions are a real design decision, not a convenience:

FunctionForBehaviour on over-precision
toMinor()request inputRejects. A write carrying more precision than the platform represents is a bug; truncating it silently would hide the bug and lose the money.
fromStored()
toMinorQuantised()		reading stored valuesQuantises, half away from zero. credits is bare numeric in the baseline, so live rows carry things like −182800.00000000000206 — an accumulated float write, seen from the database.

Keeping them separate and named rather than adding a flag is the point: quantising is a decision, and it should be visible at the call site which side of the boundary the caller is on. Getting this wrong was not hypothetical — GET /admin/reports/players and GET /admin/accounts both 400'd against production data because a read used the input parser.

Underneath: withTransaction

  • A nested call joins the outer transaction rather than opening a second one — so approving a fiat deposit can flip the deposit row and credit the player atomically.
  • Serialization failures and deadlocks are retried (40001, 40P01) with exponential backoff plus jitter, "because under betting load two players hitting the same row is normal, not exceptional."
  • lockRowsInOrder() sorts keys before locking, so an A→B and a B→A transfer at the same instant cannot deadlock — one simply waits.

The verifier that found a missing model

npm run db:verify asserts models against the live schema. The version worth having checks both directions — models against tables and tables against models — and that second direction is how a real bug surfaced:

A table with no model at all

There are two tables: bonus_history (awarded bonuses waiting to be claimed) and bonushistory (an event/amount audit log). The model generator PascalCases table names, so both wanted to be BonusHistory — and the second silently overwrote the first. The table the entire daily/weekly/monthly claim path reads and writes had no model, and the old one-directional verifier reported "every model matches". It is now hand-written as BonusClaim, so the collision cannot come back.

packages/db/src/models/extended/BonusClaim.js:11

Naming trap worth memorising

The registry is keyed by the Sequelize model name, derived from the table name. So the file is BonusHistory.js and the key is models.Bonushistory — lowercase h. Getting the capital wrong does not throw at boot; it throws Cannot read properties of undefined the first time somebody opens the screen.

Migrations

41 files, run inside a transaction, recorded in sequelize_meta. Destructive down() steps are gated behind ALLOW_DESTRUCTIVE_MIGRATION=true, and several deliberately have no down() at all — reversing them would restore a defect. Migration 013 added the unique index the spin wheel's redeem codes rely on; migration 020 gave bonushistory a primary key it had never had.

Two token families, two secrets

Player tokens are signed with JWT_ACCESS_SECRET, staff with JWT_ADMIN_SECRET, and the TokenService constructor refuses to boot if they are equal. A leaked player secret cannot mint a staff token. The type claim is checked on verify, so a refresh token cannot be presented as an access token.

Then two layers on top, and the split matters:

  • authenticate() — signature only.
  • requireActive() — re-reads status, is_locked, system_locked, bet_status from the database on every request. A token stays valid for hours; a ban must take effect now.

The VIP ladder is a pure function

Nothing stores a VIP level. It is computed from lifetime wager every time, by one shared function in packages/common — which is precisely what keeps the level shown on the VIP page and the level the bonus gate compares against from ever disagreeing.

41 levels across nine tiers (Wood, Bronze 1–5, Silver, Gold, Platinum, Jade, Sapphire, Ruby, Diamond), floors running 500 → 37,000,000. level is an ordinal number, not a name, because every consumer compares numerically; name carries the display string.

Spin wheel: the draw was predictable

The winning slice was picked with Math.random() * totalWeight. V8's Math.random is xorshift128+ — fast, uniform, and completely recoverable from a handful of consecutive outputs, after which every future draw is known. The endpoint was unauthenticated and took user_id from the body, so an attacker could sample the generator freely on throwaway accounts and then spin for real when the state said the jackpot was next.

spinWheel.service.js #draw() — three fixes in six lines
let roll = crypto.randomInt(total);
for (let i = 0; i < weights.length; i += 1) {
  if (roll < weights[i]) return i;
  roll -= weights[i];
}
  • crypto.randomInt is not predictable from its outputs.
  • roll < weights[i] replaces legacy's rand -= w; if (rand <= 0), which made slice 0 slightly more likely than its weight because a draw of exactly 0 also landed there.
  • A total weight of zero throws instead of returning slice 0 — legacy's version turned a misconfigured wheel into one that always landed on the same slice.

The cooldown is enforced by taking FOR UPDATE on the player's latest claim inside the spin transaction: the second concurrent request blocks, then reads the first's committed row and fails. A player with no history locks nothing, which is correct — their first spin is free.

The wheel awards a percentage applied to a future deposit, not cash. It writes a redeembonus row with bonus_pct set and amount: 0, and the redeem endpoint explicitly refuses those — reading amount on a percentage code would pay zero.

admin-service · 16 modules

Staff auth, RBAC, the agent hierarchy, and the audit trail every other service writes into.

Two independent ladders run the platform. Players have a flat role plus status flags. Staff have a numbered level from the roles table where lower means more authority — level 1 outranks level 5 — and level drives the agent hierarchy: a staff member can only ever act on someone strictly below them.

LvlRoleDefault grants
1Super admin*
2Admineverything except roles:manage
3Sub adminusers, wallet r/w, deposits + withdrawals approve, reports, config read
4Super masterusers, wallet r/w, casino + sports read, reports, staff read
5Masterusers r/w, wallet r/w, reports
6Agentusers read, wallet r/w, reports
7Executiveusers read, wallet read, reports read

Permissions are strings shaped resource:action — 26 of them. users:read is a specific grant, users:* covers the resource, * is unrestricted; wildcard matching is what lets a role widen without touching route definitions. The roles row in the database is authoritative and overrides these defaults.

Permissions are resolved live, not from the token

Staff grants are read from the current database role on every request, so a demoted account loses access immediately rather than when its token expires. The socket transport asks the same question: a staff member disabled at 09:00 keeps a valid eight-hour token until 17:00, so AUDIENCE.STAFF checks the row, not just the signature.

Hierarchy questions are asked, not asserted

"Whose players may this operator see?" is answered by admin-service — which owns staff — even when the asker is user-service listing wallets. The staff id comes from a verified token, so a caller cannot widen its own scope:

GET /internal/admin/staff-directory/staff/:id/descendants

Every admin write is wrapped in withActivity({ action, describe }), which writes an audit row naming the actor, the target and the details. That is why granting bonus from the counter endpoint — an action that mints balance — requires wallet:credit rather than a configuration permission, and lands in the log with the staff id attached.

What "provably fair" actually is here

This deserves stating plainly, because the naming invites a wrong assumption and the code says so itself.

The mechanism is not a provably-fair one

engine/hash.js ports legacy's generator byte for byte. makeHash() is SHA-256 of a string built from Math.random() — and hashing does not add entropy, so the result carries exactly the randomness of xorshift128+. All twenty games draw from that one generator.

More decisively: makeHash() takes no player input, and the hash is generated at the same moment as the result rather than published beforehand. So the "hash" a player is shown is not something they can verify a result against — it is a value produced alongside it. There is no client seed and no commitment.

services/casino/src/modules/in-house/engine/hash.js — header notes 1 and 2

The port isolates both properties so changing them later is a small edit rather than an archaeology exercise: the RNG is the single SEED_SOURCE function, and the "discard a winning roll when the house is up" switch is GameEngine.canProfit. Migration 004-provably-fair-seeds did add fair_server_seed, fair_server_seed_hash, fair_client_seed and fair_nonce columns — preferences.service.js deliberately excludes them from its response shape, since an unrevealed server seed is the one value that must stay secret — but no game reads them yet. The columns are laid in; the mechanism is not wired.

Singleton game loops

Crash and Keno are continuous rounds, not request/response. Legacy ran one loop per CPU worker, so which round a player saw depended on which process their socket landed on. Both loops are now singletons behind a Postgres advisory lock — chosen over a flag because it releases automatically when the connection dies, so a crashed process does not wedge the game.

sports-service · 7 modules

The exposure vector, and a two-stage settlement that is the most faithfully-ported code in the repository.

A sports bet does not resolve immediately, which changes two things: the stake is debited at placement but the payout may be days later, and open bets create liability. A player with ₹10 holding ten open ₹10 bets at 10× could win ₹1,000 the house must cover.

Exposure is a vector, not a number

This is the piece most worth understanding, and it is genuinely well-built. A player's position on a match is one signed number per possible outcome — what their balance does if that outcome happens.

A three-way cricket book
{ "India": +150.00, "Australia": -80.00, "The Draw": -80.00 }

read as: if India wins I gain 150; either other result loses me 80.

The amount that must be blocked is the worst case — the largest negative across every outcome — because that is the most the player can lose. modules/bets/exposure.js is pure functions over exact decimal strings: no database, no wallet, no request. That is deliberate, so the arithmetic deciding how much money is blocked is readable and testable on its own.

BACK at odds O for stake S:  selection +S(O−1), every other outcome −S
LAY  at odds O for stake S:  selection −S(O−1), every other outcome +S

worstCase(position)              → largest negative, or 0 if none
additionalLiability(before,after) → worstCase(after) − worstCase(before)

A hedge can pay you back mid-match. Bet the other side and your worst case shrinks, so additionalLiability is negative and funds are released. A model that only ever blocks stake × (odds−1) per bet cannot do this — it over-blocks a hedged book, sometimes by a lot.

Worked: two-way market, wallet ₹1,000
Bet 1 — back India, 100 @ 2.50 → profit 150
  book   { India: +150, Australia: −100 }
  worst  100, first bet → block 100          wallet 1000 → 900

Bet 2 — back Australia, 100 @ 3.00 → profit 200
  book   { India: +50, Australia: +100 }
  worst  0 — green either way
  delta  0 − 100 = −100 → RELEASE 100        wallet  900 → 1000

Three legacy defects are closed in this file, and each is worth knowing because each under-blocked real money:

  • The outcome list came from the request. count — the number of runners — arrived in the body, and the Draw leg was computed only if (count == 3). A three-way bet posted with count: 2 skipped the Draw entirely, so the outcome where the player loses was not in the set the worst case was taken over. Outcomes are now derived from the market.
  • Fancy exposure was switched off mid-function — the real calculation commented out above a console.log("[FANCY] Bet disabled for exposer"). A NO bet's liability is stake × (odds−1), which on a 3.0 line is twice the stake; legacy blocked the stake alone.
  • Draw names did not match consistently. The feed writes "The Draw", "Draw" and "DRAW" depending on the endpoint; legacy compared one way in one branch and another way in the next, so a draw selection matched where it was checked for and fell through as "some other team" where it was not.

Settlement is two jobs, and only one pays

JobEveryDoes
settlement:results60sFinds bets with a declared result, queues them
settlement:payout60sReads the queue. The only thing that pays anybody for a sports bet

MO/BM bets settle per user+match (because exposure is held per market, not per bet); FAN bets settle one at a time. A group that cannot resolve yet returns requeue and goes back to queued for the next tick — so a provider blip costs a minute, not a settlement.

The header is explicit that the maths did not change: settlement.rules.js holds it copied function for function, settlement.markets.js holds the market-name tables. What changed is only how rows are read and written — raw pg.query on a shared client became Sequelize models, and pg.query('BEGIN') became a real transaction.

Why that second swap is not cosmetic

Legacy issued BEGIN and COMMIT as ordinary queries on one process-wide client — legacy/General/Model/pool.js warns about this in its own header. One request's BEGIN wrapped whatever else happened to be running, and its COMMIT committed that too. Every FOR UPDATE in the legacy exposure path gave less protection than it appeared to.

One thing was deliberately not changed: processMobmGroup had no transaction in legacy — every write autocommits as it goes — and it still has none. Wrapping it would be a behaviour change, since a mid-group failure would roll back earlier bets' payouts instead of leaving them settled. That is a defensible call for a port; it is also the reason the next section exists.

Sockets

78 events across four services, on a wire protocol that cannot be changed.

All four services attach a Socket.io server to the same HTTP server, so one port serves both and the gateway needs no second upstream. A service owns the sockets that touch the things it owns.

The wire names are opaque hashes lifted byte-for-byte from legacy/General/Constant/index.js — C.SEND_TIP is "573a867973fa586555cab080e7d837ad". They are the client protocol and cannot be changed; a test pins the whole table against the legacy file, and registering an event whose name is not in the constant table throws at registration. That is the point: a typo would otherwise register a listener for a string no client sends, and the event would simply never fire with nothing to indicate why.

Same guard pattern as HTTP

A module declares an event with an audience and the transport attaches the guard, so a handler physically cannot forget its own auth check. STAFF is a separate audience rather than a flag on USER, because a player token and a staff token are different credentials issued to different tables.

Rate limits are per audience — 40 / 120 / 200 messages per 10s for public / user / staff. Legacy rate-limited nothing on this transport, including login, which made password guessing over the socket unmetered and invisible to every HTTP rate limiter in front of the service.

Two representative fixes

The one-second loop. Bonus countdowns ran setInterval at 1000ms iterating every connected socket, awaiting one database query each, sequentially. A thousand players online meant a thousand queries a second — and because each was awaited in turn, a slow one pushed the loop past its own interval and the loops piled up. All to render a countdown the client can compute from a claim_deadline it already has. Now request/response, capped at 60/min, still replying on the legacy event name so shipped clients need no change.

luckeyUsers was a module-scope array. The spin-wheel eligibility check pushed player ids into an in-process array that never shrank, was lost on restart, and existed once per forked CPU worker — so on an eight-core box the answer was eight spins. And it never spun anything: the reply was {status: true|false}, with the prize decided entirely on the client.

One more habit worth copying: if (!id) return; silently dropped the message, leaving the client on a spinner until it gave up. Every refusal now emits on the same event with { error: { code, message } }, so a client can tell "you are signed out" from "the server is slow".

The background worker

Same container, same modules, different host process.

services/sports/src/worker.js loads the same container and the same modules as the HTTP service, and runs the jobs a module declares in its manifest. That is why settlement logic lives in a service class and not a controller: automatic settlement and manual settlement run the same code, instead of the legacy arrangement where the cron carried its own copy of the payout maths.

JobIntervalNotes
feed:events60simmediate — feed:odds reads its output, so on a cold start odds would find nothing for a full minute
feed:odds2sLive books into cache, 5s TTL
settlement:results60sNot immediate — a settlement pass during boot is a poor trade for 60 seconds
settlement:payout60sClosure built once and reused, because it owns the provider rate-limit clock

Three reasons it is a separate process, all real: the odds job runs every two seconds and would put every bet placement behind a feed poll; scaling is opposite (HTTP scales to N instances, crons must effectively run once); and a provider returning malformed JSON must not take down bet placement.

Each tick is protected by a running flag — "two settlement passes over the same market is exactly the double-payout scenario" — and a failing job logs and continues rather than killing the process. REDIS_URL is required beyond local development: without it the worker caches into its own heap while the HTTP service reads its own empty one, and it warns loudly on boot rather than looking fine.

Reading it yourself

The conventions that make this codebase navigable, and the commands that produce facts instead of claims.

Four conventions worth internalising

  • @legacy METHOD /path tags are the map. Every ported handler carries one. The inventory tools read them, which is where coverage numbers come from — counted, not estimated. Grep a legacy path to find where it went.
  • The banner comment is the design record. A boxed ═══ header on a file or method means "something here was wrong and this explains it." Read those before the code; they are the most information-dense thing in the repository.
  • No raw SQL outside migrations and repositories. Every read and write goes through a Sequelize model.
  • Constants files hold every literal that appeared twice. If you find a magic number inline, its twin is probably somewhere else and out of sync — that is exactly how the bonus VIP gate came to be enforced on the read and not the claim.

Verifiers

Each of these produces a number rather than an assurance. Run them before believing any figure in a document — including this one.

npm run verify:modules    # module map + gateway rewrites all resolve
npm run verify:routes     # legacy HTTP coverage, from @legacy tags
npm run verify:sockets    # legacy socket coverage
npm run verify:models     # models vs live schema, BOTH directions
npm run verify:authz      # permission coverage on admin writes
npm run verify:internal-acl
npm run verify:secrets    # no committed credential in ported code
npm run db:status         # applied vs pending migrations
npm test                  # 71 test files, against a real PostgreSQL

Tests never mock the database away — they skip with a message if ibitplay_test is unreachable. That is why a model naming a column the database does not have is caught by db:verify in CI rather than at runtime.
